# 들어가며

상임위원회 목록이나 법안 조회 화면은 초기부터 만들어져 있었지만, 그 시점까지는 대부분 정적 데모였다. 실제 데이터가 아니라 화면 구조를 먼저 잡아둔 상태였다는 뜻이다. 이 글은 그 데모 화면들을 실제 백엔드 API로 연결하고, 그 과정에서 알림(FCM)과 이미지 공유 기능을 함께 붙인 이유를 다룬다. 실제 구현 세부사항은 [구현 문서]({% post_url 2025-04-12-barlow-front-notification-share-implementation %})에서 이어간다.

# 1. 상황: 왜 이 시점에 API 연동이었나

화면은 먼저 만들어졌지만 데이터가 실제 서버에서 오지 않는 상태로는 서비스라고 부르기 어려웠다. 홈, 최근 접수 법안, 상임위원회, 입법예고, 알림 설정, 회원가입/로그인까지 — 사용자가 앱을 켜서 마주치는 거의 모든 화면이 이 시점에 실제 API 연동 대상이었다.

동시에 두 가지가 같이 필요했다.

- **알림(FCM)**: 법안 상태가 바뀌었을 때 사용자에게 알려줄 수단이 없으면, 구독 기능 자체가 의미가 없어진다.
- **공유**: 법안 정보를 다른 사람에게 전달할 방법이 앱 내 링크 공유뿐이라면, 자연 유입 경로가 막힌다. 이미지로 캡처해서 공유하는 방식이 필요했다.

# 2. 과제

정리하면 이 시기에 동시에 처리해야 했던 건 세 갈래였다.

1. auth, home, legislation(입법), account, menu, preannounce(입법예고), recent-bill(최근 접수 법안) 등 여러 도메인의 API 요청/응답 형식을 정의하고 라우터를 추가
2. 화면들을 정적 데모 상태에서 실제 API 연결 상태로 전환
3. FCM 알림 + 이미지 공유 기능을 새로 구현

# 3. 판단: 왜 도메인별로 순차 처리했나

한 번에 모든 화면을 API에 연결하기보다, 도메인 단위(auth → home → legislation → account → menu → preannounce → recent-bill)로 API 정의와 화면 연결을 순차적으로 진행했다.

이렇게 한 이유는, 이 시점에 `core`/`feature` 아키텍처가 이미 어느 정도 자리를 잡고 있었기 때문이다. `core`에 API 클라이언트와 요청/응답 형식을 정의하고 `feature/data`에서 이를 참조하는 구조([바로앱 아키텍처 문서](https://ogongchill.github.io/posts/%EB%B0%94%EB%A1%9C%EC%95%B1%EC%95%84%ED%82%A4%ED%85%8D%EC%B3%90/)에서 다루는 DIP 원칙)를 따르고 있었기 때문에, 도메인 하나씩 API 정의 → data layer 연결 → 화면 연결까지 끝내고 다음 도메인으로 넘어가는 방식이 자연스러웠다. 한 도메인 안에서 문제가 생겨도 다른 도메인에 영향이 번지지 않는다는 것도 이 순서를 택한 이유였다.

# 4. 알림과 공유를 별도 기능이 아니라 같이 묶은 이유

FCM 알림과 이미지 공유는 표면적으로는 관계없는 기능처럼 보이지만, 둘 다 "사용자가 앱 밖에서 법안 정보를 마주치게 만드는" 진입/재진입 경로라는 공통점이 있었다.

- 알림은 이미 구독한 사용자를 다시 앱으로 불러들이는 경로
- 공유는 아직 사용하지 않는 사람에게 앱을 노출시키는 경로

그래서 이 시기에 두 기능을 같은 스프린트로 묶어서, "사용자 유입/재유입 경로를 한 번에 정리한다"는 관점으로 접근했다.

# 5. 결과

- 정적 데모였던 주요 화면(홈, 최근 접수 법안, 상임위원회, 입법예고, 알림 설정, 회원가입/로그인)이 실제 백엔드 데이터로 동작하는 상태로 전환됨
- FCM 기반 알림 센터와 이미지 공유 기능이 추가되어, 구독 기능과 자연 유입 경로가 각각 갖춰짐
- 이후 추가되는 기능들이 참조할 수 있는 도메인별 API 연동 패턴이 이 시기에 자리잡음

실제 FCM 연동 방식과 공유 이미지 생성 로직은 [구현 문서]({% post_url 2025-04-12-barlow-front-notification-share-implementation %})에서 다룬다.
