# 들어가며

'바로' 앱에는 사용자가 대표자(국회의원 등)에게 별점을 매기는 기능이 있고, 이 별점을 대표자 단위로 집계해 통계로 보여주는 기능이 있다. 이 통계 기능을 다시 손보게 된 계기는 두 가지였다 — 하나는 입력 검증 누락이었고, 다른 하나는 훨씬 심각한 개인정보 노출이었다. 실제 구현 세부사항은 [구현 문서]({% post_url 2026-05-05-baro-starpoint-stats-implementation %})에서 다룬다.

# 1. 상황: 두 가지 문제가 겹쳤다

## 1.1 입력 검증 누락

별점 UPDATE 요청 경로에 point 값의 범위 검증이 빠져 있었다. 클라이언트가 잘못된 범위의 값을 보내도 그대로 저장될 수 있는 상태였다.

## 1.2 통계 API의 개인정보 전체 노출

더 심각한 문제는 별점 통계를 제공하는 공개 엔드포인트였다. 인증 없이 호출 가능한 이 API가 연령대·성별·정치성향·거주 지역별 분포뿐 아니라, 각 분포 버킷에 속한 **사용자의 실명과 customerId까지 리스트로 그대로 반환**하고 있었다. 페이지네이션도 없어서 한 번의 요청으로 전체 목록을 그대로 긁어갈 수 있는 구조였다.

두 문제는 서로 다른 심각도였지만, 같은 별점 통계 도메인을 손보는 김에 함께 처리하기로 했다.

# 2. 과제

별점 통계 계산 로직을 대표자 단위로 제대로 구조화하면서, 다음을 함께 만족해야 했다.

1. 공개용 통계 응답에는 개인 식별 정보가 전혀 남지 않아야 한다
2. 필요하다면 개인 식별 정보를 포함한 통계는 관리자 전용 경로로 분리한다
3. 별점 등록/수정 요청에는 입력 검증이 있어야 한다
4. 반복 조회가 많은 통계 특성상 캐싱이 안정적으로 동작해야 한다

# 3. 판단: 어디까지 고칠 것인가

개인정보 노출 문제를 마주했을 때 가장 먼저 판단해야 했던 건 "통계 기능 자체를 다시 설계할 것인가, 노출된 필드만 걷어낼 것인가"였다.

응답 DTO(`CustomerStatistics`)의 구조 자체가 분포별로 `customers: List<CustomerIdAndName>`를 들고 있는 형태였기 때문에, 필드 하나만 지우는 수준으로는 근본적인 재발 방지가 안 된다고 판단했다. 그래서 통계 계산 로직 자체를 대표자 단위로 재구성하면서, 애초에 개인 식별 정보가 통계 집계 결과에 섞여 들어가지 않는 구조로 다시 짜는 쪽을 선택했다.

동시에 "이 통계를 관리자가 개인 단위로 봐야 할 필요가 있는가"도 확인했다. 완전히 없앨 수는 없는 요구였기 때문에, 공개 엔드포인트와 관리자 엔드포인트를 분리하는 방향으로 결론을 냈다.

# 4. 결과

point 범위 검증 누락으로 인한 데이터 무결성 문제를 해소했고, 통계 기능을 공개/관리자용으로 구조적으로 분리한 뒤 테스트로 검증했다. 개인정보 노출이 제기됐던 이슈는 close 처리됐다.

이 사례는 이후 API를 설계할 때 "통계·집계 응답에 원본 개인 식별 데이터가 섞여 들어갈 수 있는가"를 별도로 점검하게 만든 계기가 됐다. 기술적인 리팩터링 과정은 [구현 문서]({% post_url 2026-05-05-baro-starpoint-stats-implementation %})에서 이어진다.
