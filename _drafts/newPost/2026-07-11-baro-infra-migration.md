의안·정치인 조회 서비스 '바로'의 백엔드를 레거시(수동 EC2 운영)에서 신규 아키텍처로 옮기는 과정에서, 인프라를 콘솔 클릭 대신 코드로 관리하는 기반을 새로 만들고 그 위에 dev 오토스케일링, prd 무중단 배포, 레거시 배치 서버 CI/CD까지 순서대로 얹었습니다. 이 글은 "왜 이 순서로, 왜 이 도구를 선택했는가"를 정리한 것이고, 구체적인 장애 원인과 수정 내역은 [구현 문서](/2026/07/11/baro-infra-migration-implementation)에 별도로 정리했습니다.

## 1. 왜 Terraform부터 시작했는가

### 문제 상황

신규 백엔드(baro-backend)가 이관받을 기존 AWS 인프라—EC2, RDS, S3, ALB, CloudFront, WAF, 보안그룹, IAM—는 콘솔에서 수동으로 관리되고 있었습니다. 누가 언제 무엇을 바꿨는지 이력이 남지 않고, 같은 환경을 재현하려면 콘솔 클릭을 그대로 재연해야 하는 상태였습니다.

### 과제와 제약

이후 예정된 작업(dev 오토스케일링 전환, CI/CD, prd 무중단 배포)이 전부 이 인프라 위에 쌓일 예정이었기 때문에, 순서를 바꿔서 CI/CD부터 만들면 코드화되지 않은 리소스 위에 파이프라인을 얹는 꼴이 됩니다. 그래서 가장 먼저 기존 계정 리소스를 하나의 Terraform state로 편입시키는 작업을 우선순위로 잡았습니다.

### 범위를 의도적으로 좁힌 이유

계정 안의 모든 리소스를 다 끌어오지는 않았습니다. 서버 구성과 무관한 SSO/IAM 거버넌스 리소스, 더 이상 쓰지 않는 Lambda/SNS 파이프라인은 추적 대상에서 제외했습니다. Terraform import는 "관리하는 리소스"와 "존재하지만 건드리지 않는 리소스"의 경계를 명확히 긋는 작업이기도 해서, 실제 배포 파이프라인이 손대는 범위만 좁게 가져가는 쪽을 택했습니다.

## 2. Dev 환경: 왜 ALB+ASG로 먼저 갔는가

Terraform 기반이 마련된 뒤 첫 목표는 dev 환경을 실제 운영 가능한 형태로 끌어올리는 것이었습니다. 여기서 오토스케일링을 먼저 넣은 이유는, 이후 CI/CD가 배포할 대상 자체가 고정 인스턴스가 아니라 ASG 기반이어야 롤링 교체가 자연스럽기 때문입니다. Golden AMI(Packer로 빌드) + Launch Template + ASG 조합을 선택한 것도 같은 이유로, 배포 시점마다 새 AMI를 굽고 ASG가 교체하는 구조가 "배포 = 인스턴스 재배치"라는 CI/CD 흐름과 맞아떨어졌습니다.

앱 시크릿도 이 시점에 SSM SecureString 주입 방식으로 전환했는데, AMI가 매번 새로 만들어지는 구조에서는 시크릿을 AMI 안에 굽거나 배포 스크립트에 하드코딩할 수 없었기 때문입니다.

## 3. Prd 환경: 왜 Blue/Green을 선택했는가

Dev CI/CD가 안정화된 뒤 prd에도 같은 방식(단순 ASG 교체)을 쓸 수도 있었지만, prd는 무중단이 필수 조건이었습니다. 롤링 배포는 배포 중 신버전/구버전이 동시에 트래픽을 받는 구간이 생기고, 문제가 생겼을 때 되돌리는 절차도 복잡합니다. CodeDeploy 기반 Blue/Green을 선택한 이유는:

- 신규 버전을 별도 ASG(Green)에 완전히 띄운 뒤 헬스체크를 통과해야 트래픽을 전환하므로, 배포 실패가 서비스 장애로 이어지지 않는다
- 문제 발생 시 ALB 라우팅을 이전 ASG(Blue)로 되돌리기만 하면 되므로 롤백이 "재배포"가 아니라 "스위치"에 가깝다

다만 이 선택에는 비용 트레이드오프가 따릅니다. 배포 중 한동안 Blue/Green 두 세트의 인스턴스가 동시에 떠 있어야 하므로 순간적으로 컴퓨트 비용이 두 배가 됩니다. 상시 운영 비용이 아니라 배포 시점에만 발생하는 비용이라 감수할 만하다고 판단했습니다.

또한 prd 배포 트리거 방식을 git tag 기반에서 Slack 커맨드 기반으로 바꿨습니다. tag push는 로컬 git 상태에 의존하고 실수로 잘못된 커밋에 태그를 찍기 쉬운 반면, Slack 커맨드는 "지금 이 아티팩트를 이 환경에 배포한다"는 의도를 명시적으로 드러내고, 상태 조회·취소까지 같은 인터페이스로 묶을 수 있었습니다. develop/release 브랜치 직접 push를 막는 pre-push hook을 추가한 것도 같은 맥락으로, 배포는 반드시 정해진 경로(Slack 커맨드)를 통하도록 강제한 조치입니다.

## 4. 레거시 배치 서버 CI/CD: 왜 신규 스택과 다른 선택을 했는가

레거시 배치 서버(batch)는 신규 백엔드와 별개로, macmini(Apple Silicon, 온프레미스)에서 계속 돌아가고 있는 시스템이었습니다. "레거시 레포에 추가 투자하지 않는다"는 방침이 있었기 때문에, 이 서버는 새 아키텍처로 옮기는 대신 딱 필요한 만큼—push하면 자동으로 빌드되어 macmini까지 전달되는 최소 CI/CD—만 구축했습니다.

빌드 실행 주체를 고르는 과정에서 몇 차례 방향이 바뀌었습니다: GitHub PAT는 지양 방침 때문에 배제, SSM 하이브리드 활성화로 macmini를 직접 관리 대상에 넣는 방안은 AWS 공식 문서 확인 결과 macOS(non-EC2)가 SSM 하이브리드를 지원하지 않아 무산, GitHub Actions 셀프호스티드 러너 대안도 검토했지만 반려되어 최종적으로 CodeBuild + 기존 CodeConnections 재사용으로 정리했습니다. 이 과정에서 겪은 인증 오류의 근본 원인과 아키텍처 불일치 문제는 [구현 문서](/2026/07/11/baro-infra-migration-implementation)에서 다룹니다.

## 정리

인프라를 코드화하고, 그 위에 dev 오토스케일링과 CI/CD, prd 무중단 배포를 순서대로 쌓은 흐름이었습니다. 매 단계에서 "이 도구가 이후 단계의 전제 조건이 되는가"를 기준으로 선택했고 — Terraform 없이는 재현 가능한 dev 환경을 만들 수 없고, ASG 없이는 CI/CD가 배포할 안정적인 대상이 없고, Blue/Green 없이는 prd 무중단이 성립하지 않는 식입니다. 레거시 배치 서버는 같은 기준을 적용하지 않고 "방침에 맞는 최소 구현"으로 별도 트랙을 잡은 것도 같은 원칙의 다른 결론이었습니다.
