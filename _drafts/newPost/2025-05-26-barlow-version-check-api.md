# 들어가며

Barlow는 아직 비공개 트랙으로 배포되는 단계였고, Flutter로 빌드되는 클라이언트 버전은 `1.0.0-alpha`였다. 정식 출시가 가까워지면서 "클라이언트 버전을 서버가 알고, 필요하면 업데이트를 유도하거나 아예 요청을 막을 수 있어야 한다"는 요구가 생겼다. 이 글은 그 배경과 설계 결정을 정리한 것이고, 실제 구현 내용은 [구현 문서]({% post_url 2025-06-02-barlow-version-check-api-implementation %})에서 다룬다.

# 1. 왜 필요했나

작은 팀이 앱스토어 심사 주기를 거쳐 배포하는 구조에서는, 서버 API가 먼저 바뀌고 클라이언트가 그 변경을 따라가지 못하는 시차가 항상 생긴다. 이 시차 동안 구버전 클라이언트가 계속 요청을 보내면:

- 서버가 이미 없앤 필드/스펙에 의존하는 요청이 들어와 에러가 나거나
- 반대로 서버가 구버전 클라이언트를 계속 지원해야 하는 부담이 생긴다

그래서 앱 시작 시점에 "이 버전이 아직 쓸 수 있는 버전인가"를 서버에 물어보고, 상황에 따라 인앱 업데이트를 유도하거나 아예 요청을 차단할 수 있는 구조가 필요했다.

추가로 고려한 문제 하나는 "서버 호스팅 주소 자체가 바뀌는 경우"였다 — 이 경우 클라이언트는 새 주소로 요청을 보낼 방법이 없으니 버전 확인 API 자체도 무력화된다. Firebase Remote Config으로 우회하는 방법도 검토했지만, "사용자 승인 없는 업데이트 유도에 Remote Config을 쓰지 말라"는 정책에 걸릴 수 있어 채택하지 않았다. 결론은 "프로덕션 빌드 전에 호스팅 주소를 확정한다"는 운영상의 제약으로 남겨두고, 버전 확인 자체에 집중하기로 했다.

# 2. 무엇을 만족해야 했나

플랫폼(Android/iOS)별로 최소 지원 버전(`min_supported_version`)과 최신 버전(`latest_version`)을 서버가 관리하고, 클라이언트가 시작 시 물어보면 다음 흐름으로 응답해야 했다.

```
[클라이언트 앱 시작]
       ↓
[API 서버에 버전 확인 요청]
       ↓
[서버에서 플랫폼/버전 기반 판별]
       ↓
[응답: 업데이트 필요 여부]
       ↓
[클라이언트에서 인앱 업데이트 또는 차단 처리]
```

여기서 판별 기준을 어떻게 정의할지가 설계의 핵심이었다. 단순히 "최신 버전과 다르면 업데이트"가 아니라, 아래 네 가지 상태를 구분해야 했다.

- **LATEST**: 요청 버전이 최신 버전과 동일
- **UPDATE_AVAILABLE**: 최소 지원 버전 이상이지만 최신 버전보다 낮음 (업데이트 권장, 차단은 아님)
- **NEED_FORCE_UPDATE**: 최소 지원 버전보다 낮음 (강제 업데이트 필요)
- **INVALID**: 정책상 임의로 차단된 버전 (예: 비공식 릴리즈를 운영에서 막는 경우)

# 3. 설계 결정

## 3.1 버전 비교 규칙은 SemanticVersion을 기준으로

버전 우선순위 비교를 문자열 비교나 산발적인 조건문으로 처리하면 `1.0.0-alpha`와 `1.0.0-rc` 같은 프리릴리즈 순서를 정확히 표현하기 어렵다. [SemVer](https://semver.org/) 규칙을 기준으로 도메인 계층에 `SemanticVersion` 값 객체를 두고, 이 객체가 자체적으로 하위 버전 여부(`isLessThan`)를 판단하게 했다.

정식 릴리즈(`<major>.<minor>.<patch>`)와 비공식 릴리즈(`<major>.<minor>.<patch>-<suffix>`)를 구분하고, `snapshot < alpha < beta < rc < 정식 릴리즈` 순으로 우선순위를 정의했다. 이렇게 규칙을 도메인 객체 하나에 모아두면, 이후 판별 로직(LATEST/UPDATE_AVAILABLE/...)은 이 객체에 위임하기만 하면 된다.

## 3.2 비공식 릴리즈 허용 여부를 전략으로 분리

개발 중에는 `alpha`/`beta`/`rc` 같은 비공식 릴리즈 버전도 정상적으로 써야 하지만, 정식 운영 단계에서는 이런 버전을 아예 차단하고 싶을 수 있다. 이 정책을 판별 로직 안에 조건문으로 박아두는 대신, 전략(Strategy) 객체로 분리해 `@Profile` 설정만으로 전환 가능하게 했다 — 지금 당장은 모든 비공식 릴리즈를 허용하되, 운영 전환 시점에는 설정 변경만으로 비공식 버전을 `INVALID`로 차단할 수 있게 여지를 남겨둔 것이다.

## 3.3 처음 구현이 브랜치 사고로 날아간 것

이 작업 도중, `issue/97` 브랜치에 의도치 않은 내용이 잘못 푸시되는 사고가 있었다. 이미 구현해둔 도메인/저장소/컨트롤러 전체를 일단 되돌리고, PR #98에서 전체를 다시 구현해 병합했다 — 설계 자체는 처음 방향과 같았지만, 브랜치 정리 과정에서 한 번 처음부터 다시 쓴 셈이다.

# 4. 결과

`api/v1/client-version/check` 엔드포인트가 병합되어, 요청 헤더의 디바이스 OS·앱 버전을 기준으로 업데이트 필요 여부를 응답하게 됐다. 다만 이 시점에 배치 설정이 없어 storage 계층 테스트는 실행 확인이 되지 않은 채로 남았고, 버전 정보 캐싱 전략을 더 정교하게 다듬는 것도 후속 과제로 남겨뒀다.
