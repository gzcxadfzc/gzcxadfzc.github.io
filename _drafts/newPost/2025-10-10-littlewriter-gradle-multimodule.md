# 들어가며

LittleWriter를 약 1년 만에 v2로 다시 붙잡았을 때, 가장 먼저 마주친 건 새 기능이 아니라 예전 코드베이스였다. 단일 Gradle 모듈 안에 도메인 로직, API, 인증, JPA/Redis/S3 연동, OpenAI 호출이 전부 같은 `com.pkg` 패키지 트리 아래 뒤섞여 있었다. 이 글은 그 구조를 `domain`/`api`/`auth`/`storage`/`ai`/`core` 6개 Gradle 모듈로 쪼갠 이유를 정리한 것이다. 실제 모듈 구조와 마이그레이션 과정은 [구현 문서]({% post_url 2025-10-19-littlewriter-gradle-multimodule-implementation %})에서 다룬다.

이 리팩터링은 도메인 계층을 AI 구현체로부터 분리한 아키텍처 변경(별도로 [여기]({% post_url 2025-11-19-littleWriter02 %})에서 다뤘다)과 같은 시기에 진행됐지만, 서로 다른 문제를 겨냥한다. 그 글이 "도메인이 어떤 인터페이스에 의존하는가"를 다뤘다면, 이 글은 "그 경계를 컴파일 타임에 어떻게 강제하는가"를 다룬다.

# 1. 상황: 패키지 컨벤션만으로는 경계가 지켜지지 않는다

단일 모듈 구조에서도 `domain`, `api`, `storage` 같은 패키지는 나뉘어 있었다. 문제는 패키지 분리가 **관례**일 뿐 **강제**가 아니라는 점이었다.

- 아무 패키지에서나 아무 패키지의 클래스를 import할 수 있어서, 도메인 코드가 JPA 엔티티나 OpenAI 클라이언트를 직접 참조하는 코드가 시간이 지나며 슬금슬금 늘어났다.
- 코드 리뷰에서 "이건 도메인 계층에서 하면 안 되는 참조 아닌가"를 매번 사람이 걸러야 했다.
- 모듈이 하나이므로 아주 사소한 변경(예: OpenAI 클라이언트 코드 수정)도 전체 코드베이스를 다시 컴파일해야 했다.

# 2. 과제: 경계를 컴파일러가 강제하게 만들기

목표는 명확했다. "도메인 계층은 인프라를 몰라야 한다"는 규칙을 코드 리뷰가 아니라 빌드 시스템이 강제하도록 만드는 것.

Gradle 멀티모듈에서는 모듈 간 의존성이 `build.gradle.kts`의 `dependencies { }` 블록에 명시적으로 선언되고, 선언되지 않은 모듈의 클래스는 애초에 클래스패스에 없어 import 자체가 불가능하다. 패키지 컨벤션과 달리 이건 사람이 아니라 컴파일러가 지켜주는 경계다.

# 3. 설계: 어떤 기준으로 모듈을 나눴나

## 3.1 domain을 의존성 그래프의 뿌리로

`domain` 모듈은 다른 어떤 모듈에도 의존하지 않도록 설계했다. Spring 프레임워크에도 최소한으로만 의존한다(`spring-context`, 그것도 `compileOnly`). JPA, Redis, AWS SDK, OpenAI 클라이언트 — 이런 인프라 의존성은 domain 모듈의 `build.gradle.kts`에 아예 추가할 수 없는 구조로 만들었다. 추가하려는 순간 "이건 도메인이 알아야 할 게 아니다"라는 신호가 명확하게 드러난다.

## 3.2 api/auth/storage는 domain만 바라본다

`api`, `auth`, `storage` 세 모듈은 각각 `implementation(project(":domain"))` 또는 `compileOnly(project(":domain"))`로 domain만 의존하고, 서로를 직접 참조하지 않는다. 즉 storage가 api를 알거나 auth가 storage를 아는 구조는 애초에 만들 수 없다. 모든 모듈이 domain을 중심으로 방사형으로 연결되는 구조를 강제한 것이다.

## 3.3 ai 모듈은 독립적으로 뺐다

AI 연동(OpenAI, 이미지 생성)은 처음부터 별도 모듈로 분리했다. 이유는 두 가지였다.

- **교체 가능성**: 생성형 AI 쪽은 모델·API가 가장 빠르게 바뀌는 영역이라, 다른 모듈과 얽히지 않게 격리해두는 편이 이후 교체 비용을 낮춘다.
- **독립적인 빌드/테스트**: ai 모듈만 따로 컴파일·테스트할 수 있으면, AI 연동 로직을 수정할 때 storage나 auth까지 다시 빌드할 필요가 없다.

# 4. 결과

`domain`/`api`/`auth`/`storage`/`ai`/`core` 6개 모듈로 나누고, domain을 의존성 그래프의 뿌리로 둔 방사형 구조를 완성했다. 이 구조는 이후 v2 API(인증/도서/캐릭터)를 다시 구현할 때, "이 로직을 어느 모듈에 둬야 하는가"라는 질문에 대한 답을 설계 단계에서부터 명확하게 만들어줬다.

실제 모듈별 `build.gradle.kts` 구성과, storage/ai 모듈 내부를 정리하며 겪은 문제는 [구현 문서]({% post_url 2025-10-19-littlewriter-gradle-multimodule-implementation %})에서 이어진다.
