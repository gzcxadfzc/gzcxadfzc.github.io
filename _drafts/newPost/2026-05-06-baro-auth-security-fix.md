# 들어가며

레거시 백엔드 코드를 훑어보던 중, 로그인·비밀번호 변경·외부 본인인증 연동처럼 민감한 흐름이 여전히 `GET` 요청 파라미터로 아이디·비밀번호를 주고받고 있다는 걸 발견했다. 오래된 API일수록 관례적으로 GET을 써 온 흔적이 남아있기 마련인데, 하필 그 관례가 인증 도메인에 그대로 남아 있었던 셈이다.

이 글은 취약점을 발견한 경위와, 그걸 얼마나 급하게 얼마나 크게 고칠지 판단한 과정을 정리한 것이다. 구체적인 코드 변경 내용은 [구현 문서]({% post_url 2026-05-06-baro-auth-security-fix-implementation %})에서 다룬다.

# 1. 무엇이 문제였나

## 1.1 발견 경위

인증 모듈을 다른 이유로 들여다보다가, 로그인 및 비밀번호 관련 요청 몇 개가 GET 쿼리 파라미터에 아이디·비밀번호·인증정보를 실어 보내고 있다는 걸 확인했다. 함께 붙어있던 유틸성 엔드포인트 중에는 정상적인 인증 절차 없이도 신원 확인이 되는 경로가 운영 환경에 그대로 남아있는 경우도 있었다.

## 1.2 왜 문제인가

GET 파라미터로 전달된 값은 개발자가 직접 로그를 남기지 않아도 여러 지점에 평문으로 흔적을 남긴다.

- **서버 액세스 로그**: 대부분의 웹 서버/리버스 프록시는 요청 URL 전체를 access log에 기록한다. 쿼리 파라미터도 예외가 아니다.
- **브라우저 히스토리**: 클라이언트가 GET으로 요청을 보내는 경로였다면, 브라우저 히스토리에도 그대로 남는다.
- **중간 프록시/로드밸런서 로그**: 인프라 구성에 따라 하나의 요청이 여러 로깅 지점을 거치는데, 각 지점마다 노출 지점이 늘어나는 셈이다.

즉 한 곳만 막아서 되는 문제가 아니라, 이 값이 지나가는 모든 경로가 잠재적 노출 지점이 된다는 게 핵심이었다.

추가로, 정상 인증 절차를 우회할 수 있는 여지가 있는 보조 엔드포인트가 운영 환경에 남아있었던 것도 함께 확인됐다 — 개발/디버깅 단계에서 편의를 위해 추가했다가 운영 배포 시 제거되지 않은 사례로 보였다.

## 1.3 우선순위 판단

이 이슈를 마주했을 때 가장 먼저 한 판단은 "얼마나 급한가"였다.

- 인증 정보가 로그로 흘러 들어가는 구조는, 로그 접근 권한을 가진 누군가(혹은 로그 수집/전송 파이프라인의 취약점)만 있으면 실제 피해로 이어질 수 있는 사안이라 **재현 난이도와 무관하게 최우선으로 처리**해야 한다고 판단했다.
- 반면 근본적인 인증 아키텍처(세션/토큰 방식 등)를 다시 설계하는 건 별개의 작업이라, **이번 대응 범위는 "민감 정보가 URL에 실리지 않게 만드는 것"으로 한정**했다. 범위를 넓히면 검증해야 할 회귀 범위도 함께 커지기 때문에, 취약점 대응은 좁고 빠르게 가져가는 쪽을 택했다.

# 2. 대응 방향

## 2.1 선택한 방식

로그인/비밀번호 변경/외부 인증 연동과 관련된 요청들을 **GET + 쿼리 파라미터 → POST(또는 PUT) + Request Body** 방식으로 전환하기로 했다.

이 방식을 택한 이유:

- **가장 확실한 차단점**: HTTP 스펙상 body는 access log나 히스토리에 남지 않는다. URL 자체에 민감 정보가 실리지 않으니, 로깅 인프라를 하나하나 손보지 않아도 노출 경로 자체가 사라진다.
- **변경 범위가 예측 가능함**: 메서드/파라미터 바인딩 방식만 바꾸면 되므로, 비즈니스 로직을 건드릴 필요가 없어 회귀 리스크가 낮다.
- **표준적인 관례에 맞음**: 민감 정보를 다루는 API는 POST + Body가 일반적인 관례이기도 해서, 이후 유지보수 시에도 자연스러운 패턴이 된다.

## 2.2 함께 정리한 것

운영 환경에 남아있던, 정상 인증 절차를 생략할 수 있는 보조 엔드포인트도 함께 제거 대상으로 판단했다. 이런 종류의 엔드포인트는 재현 조건이나 위치를 공개하는 것 자체가 위험하므로 이 글에서는 구체적으로 다루지 않는다 — 다만 "개발 편의용으로 추가한 우회 경로가 배포 체크리스트에서 걸러지지 않으면 운영 환경까지 따라온다"는 교훈만 남겨둔다.

# 3. 결과

민감 정보가 URL에 노출되던 경로들을 body 기반으로 전환하고, 우회 가능했던 보조 엔드포인트를 정리했다. 관련 이슈는 close 처리됐다.

이 작업을 계기로, 이후 신규 API를 리뷰할 때 "민감한 값이 URL에 실릴 수 있는가"를 체크리스트 항목으로 명시적으로 넣게 됐다. 구조적인 예방보다 이런 관례/체크리스트 수준의 대응이 당장은 더 현실적이라고 판단했기 때문이다.
