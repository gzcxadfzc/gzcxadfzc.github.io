# 들어가며

'바로' 앱은 화면이 하나둘 늘어나면서 TopBar, TabBar, Card 같은 기본적인 UI 요소들이 화면마다 따로 구현되고 있었다. 이 글은 그 상태를 재사용 가능한 디자인 시스템으로 정리한 과정을 다룬다. 실제 컴포넌트 구조와 구현 방식은 [구현 문서]({% post_url 2026-05-14-baro-design-system-implementation %})에서 다룬다.

# 1. 상황: 왜 흩어져 있었나

화면을 하나씩 빠르게 만들다 보면 자연스럽게 벌어지는 일이다. 상단바가 필요하면 그 화면 안에 상단바를 만들고, 탭이 필요하면 그 화면에 맞는 탭을 만든다. 처음 한두 화면에서는 문제가 안 되지만, 화면이 늘어나면 같은 모양의 TopBar/TabBar/Card가 화면 개수만큼 조금씩 다르게 존재하게 된다.

'바로' 앱에서 실제로 이런 상태였던 요소들:

- **TopBar** — 화면마다 개별 구현
- **TabBar / BottomNavBar** — 탭마다 흩어져 있던 구현
- **Card류** — 입법 카드, 소식 카드, Election 카드가 각각 다른 스타일로 구현
- **SegmentControl, ChipSelector, Pill** — 필터/선택 UI가 화면별로 제각각
- **ListSection** — 리스트 화면 레이아웃 패턴이 반복되지만 공유되지 않음

# 2. 과제: 무엇을 갖춰야 했나

단순히 컴포넌트를 몇 개 빼내는 것으로는 부족했다. 확정해야 했던 건 크게 두 가지였다.

1. **재사용 가능한 UI 프리미티브 세트** — TopBar부터 ListSection까지, 화면 어디서든 조합해서 쓸 수 있는 형태
2. **컴포넌트를 어떻게 만들지에 대한 규칙** — 디자인 시스템은 한 번 만들고 끝나는 게 아니라 계속 확장되기 때문에, 다음에 컴포넌트를 추가하는 사람(미래의 나 포함)이 같은 패턴을 따르게 만드는 게 오히려 더 중요했다

# 3. 설계: 우선순위와 패턴

## 3.1 왜 한 번에 다 만들지 않았나

`components/ui/`를 신설하면서 모든 컴포넌트를 한 번에 설계하려 하지 않았다. TopBar/Border/Divider처럼 가장 자주 쓰이고 단순한 것부터 만들어 탭 레이아웃에 바로 적용해보고, 그 다음 TabBar/BottomNavBar를 공통화하는 식으로 우선순위를 두고 순차적으로 진행했다.

이렇게 한 이유는 디자인 시스템을 추상적으로 설계하면 실제 화면에서 안 맞는 부분이 뒤늦게 발견되기 때문이다. 컴포넌트 하나를 만들 때마다 바로 실제 화면(홈 탭, explore, digest, 우리동네)에 적용해보면서 API를 다듬는 쪽이 더 빨랐다.

## 3.2 왜 Card류를 compound 컴포넌트로 만들었나

입법 카드, 소식 카드, Election 카드는 레이아웃 골격은 같지만 내부 콘텐츠 구성이 조금씩 다르다. 이런 경우 `<Card title="..." subtitle="..." ... />`처럼 props를 계속 늘리는 방식은 카드 종류가 늘어날수록 props가 기하급수적으로 늘어난다.

대신 `Card.Header`, `Card.Body`처럼 조합해서 쓰는 compound 패턴을 택했다. 각 카드 종류는 필요한 하위 컴포넌트만 골라 조합하면 되고, Card 자체는 공통 레이아웃/스타일 토큰만 책임진다. `ListSection`도 같은 이유로 compound 패턴을 따랐다.

## 3.3 왜 규칙을 문서로 남겼나

컴포넌트를 다 만든 뒤 `ui-rules.md`로 작성 규칙을 문서화했다. 디자인 시스템의 가장 큰 리스크는 "처음엔 잘 지켜지다가 규칙 없이 컴포넌트가 하나둘 추가되면서 다시 흩어지는 것"이라고 판단했기 때문이다. 이번에 정리한 패턴(compound 컴포넌트, 네이밍, 토큰 사용 방식)을 규칙으로 남겨서, 앞으로 컴포넌트가 추가될 때도 같은 기준을 따르게 만드는 게 목적이었다.

# 4. 결과

TopBar/TabBar/BottomNavBar/Card/SegmentControl/ChipSelector/ListSection까지 화면마다 중복 구현되던 UI 요소들을 `components/ui/` 아래 공통 컴포넌트로 통합했고, 홈/explore/digest/우리동네 탭 전역에 적용했다. 컴포넌트 작성 규칙 문서화로 이후 UI 개발에 일관된 가이드라인도 마련했다.
