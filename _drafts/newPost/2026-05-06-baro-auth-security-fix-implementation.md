# 들어가며

[설명 문서]({% post_url 2026-05-06-baro-auth-security-fix %})에서 다룬 취약점의 실제 수정 방식을 정리한다. 이 글은 다른 서비스에서 비슷한 문제를 마주쳤을 때 참고할 수 있는 **일반적인 수정 패턴**을 목적으로 쓴다. 재현 가능한 수준의 구체적인 엔드포인트 경로나 파라미터명은 의도적으로 생략했다 — 이미 조치는 완료됐지만, 같은 패턴의 문제가 다른 곳에 남아있을 가능성을 고려해서다.

# 1. 문제가 있던 패턴

민감 정보를 다루는 요청 몇 개가 대략 아래와 같은 형태로 구현돼 있었다.

```kotlin
// 문제가 있던 패턴 (개념적 예시, 실제 시그니처 아님)
@GetMapping("/some-auth-endpoint")
fun handle(
    @RequestParam id: String,
    @RequestParam sensitiveValue: String
): ResponseEntity<BaseResp> { ... }
```

`@RequestParam` + `GET`은 스펙상 값이 URL 쿼리 스트링에 실린다는 뜻이고, 이는 곧 [설명 문서]({% post_url 2026-05-06-baro-auth-security-fix %})에서 짚은 로그/히스토리 노출 경로로 직결된다.

# 2. 수정 패턴

## 2.1 GET → POST/PUT + Body 전환

핵심 수정은 HTTP 메서드와 파라미터 바인딩 방식을 바꾸는 것이었다.

```kotlin
// 수정 후 (개념적 예시)
@PostMapping("/some-auth-endpoint")
fun handle(
    @RequestBody dto: AuthRequestDto,
    response: HttpServletResponse
): ResponseEntity<BaseResp> { ... }
```

바꾼 지점은 크게 세 종류였다:

1. **로그인 요청**: 아이디/비밀번호를 담아 인증을 수행하는 요청
2. **비밀번호 변경/재설정 요청**: 현재 비밀번호 또는 새 비밀번호를 담아 전달하는 요청
3. **외부 본인인증 연동 요청**: 외부 인증 서비스와 연동되는 과정에서 민감한 값이 함께 전달되는 요청

세 경우 모두 공통적으로 `@RequestParam` 기반 GET 핸들러를 `@RequestBody` 기반 POST/PUT 핸들러로 바꾸고, 값을 담던 개별 파라미터들을 전용 Request DTO로 묶었다.

```kotlin
data class AuthRequestDto(
    val id: String,
    val sensitiveValue: String
)
```

DTO로 묶는 게 필수는 아니지만, ① Kotlin에서 `@RequestBody`는 단일 객체를 기대하기 때문에 구조적으로 필요했고 ② 이후 검증 로직(`@field:NotBlank` 등)을 DTO 레벨에 붙이기 편해지는 부수 효과도 있었다.

## 2.2 우회 가능했던 보조 엔드포인트 정리

정상 인증 절차 없이도 신원 확인이 가능했던 보조 엔드포인트는 코드베이스에서 제거했다. 이런 종류의 엔드포인트가 왜 위험한지에 대한 일반론만 남긴다:

- 개발/디버깅 편의를 위해 인증을 생략한 경로를 임시로 추가하는 경우가 있는데, **feature flag나 profile 분기 없이 코드에 그대로 남아있으면 운영 배포와 함께 그대로 살아남는다.**
- 이런 경로는 정상 트래픽 패턴과 크게 다르지 않아 access log 모니터링만으로는 발견하기 어렵다. 코드 리뷰나 정기적인 엔드포인트 인벤토리 점검처럼, **로그 기반이 아닌 방식의 탐지 체계**가 필요하다는 걸 확인한 계기였다.

## 2.3 클라이언트 측 변경

서버가 GET에서 POST/PUT + Body로 바뀌면 클라이언트 쪽 요청 코드도 함께 바뀌어야 한다. 이 변경은 인증처럼 호출 지점이 제한적인 도메인이라 클라이언트 반영 범위가 크지 않았고, 서버·클라이언트 배포 순서만 맞추면 되는 수준이었다.

# 3. 검증

- 변경된 각 엔드포인트에 대해 요청이 정상적으로 body를 통해 처리되는지 확인
- 기존 GET 방식으로의 접근이 더 이상 동작하지 않는지(404/405) 확인
- 실제 access log 샘플을 통해 더 이상 민감 값이 쿼리 스트링에 남지 않는지 재확인

# 4. 일반화한 체크리스트

이후 신규 API 리뷰 시 참고하려고 정리해 둔 체크리스트:

- [ ] 이 엔드포인트가 다루는 값 중 인증/개인정보에 해당하는 게 있는가?
- [ ] 그 값이 URL(쿼리 파라미터, path variable)에 실리는가?
- [ ] 인증을 생략하거나 우회할 수 있는 보조/디버그 경로가 이 도메인에 함께 존재하는가?
- [ ] 그 경로가 profile 분기 없이 운영 환경 빌드에도 포함되는가?

체크리스트 자체는 단순하지만, 이번 사례처럼 "관례적으로 GET을 써 온 오래된 코드"에는 의외로 자주 해당될 수 있다는 걸 배웠다.
