# 들어가며

바로 앱을 만들면서 기능 구현 못지않게 시간을 들인 게 세 가지 있다. 저장소 상태를 Slack으로 알려주는 파이프라인, 빌드부터 배포까지 자동으로 이어지는 CI/CD, 그리고 core/feature 경계를 정리해 카카오 로그인을 무리 없이 얹을 수 있는 구조. 셋 다 기능 자체는 화려하지 않지만, 팀이 작아서 한 사람이 기획·개발·배포를 다 챙겨야 하는 상황에서는 오히려 이런 자동화/구조 정리가 체감 생산성에 더 크게 기여했다.

이 글에서는 왜 이 세 가지를 이 순서로, 이런 방식으로 했는지를 다룬다. 실제 워크플로우 구성과 코드는 [구현 문서]({% post_url 2026-02-27-barlow-front-cicd-auth-implementation %})에서 이어간다.

# 1. 저장소 상태를 Slack으로: 왜 필요했나

## 1.1 상황

여러 브랜치에서 동시에 작업이 진행되는데, PR이나 이슈 상태를 확인하려면 매번 GitHub을 직접 열어야 했다. 저장소 상태를 한눈에 파악할 수 있는 채널이 없다는 게 문제였다.

## 1.2 판단

Slack 알림을 붙이기로 한 이유는 단순하다 — 이미 팀 커뮤니케이션이 Slack에서 이뤄지고 있었기 때문에, 별도로 대시보드를 보러 가는 것보다 상태가 알아서 Slack으로 흘러들어오는 쪽이 확인 비용이 훨씬 낮았다. GitHub Actions + GraphQL API로 브랜치/PR/이슈 상태를 주기적으로 조회해서 Slack으로 보내는 구조를 택했다.

# 2. CI/CD: 수동 배포가 한계에 부딪힌 시점

## 2.1 상황

앱을 1.0.0 정식 버전으로 전환하는 시점이 되자, 수동으로 빌드하고 배포하는 방식은 반복 검증에 비효율적이었다. 배포할 때마다 로컬에서 빌드하고 스토어에 업로드하는 과정을 사람이 직접 챙기다 보니, 실수가 끼어들 여지도 컸다.

## 2.2 과제

빌드(`ci.yml`)와 배포(`cd.yml`)를 GitHub Actions로 자동화하고, 실제로 여러 버전을 거치며 안정적으로 도는 상태까지 만드는 게 목표였다.

## 2.3 판단

처음부터 완벽한 파이프라인을 설계하기보다, 일단 최소 동작하는 파이프라인을 만들고 실제 배포(버전 10 → 24)를 거치며 반복적으로 고쳐나가는 방식을 택했다. 이유는 배포 자동화는 로컬에서 재현하기 어려운 실패 케이스(서명, 스토어 정책, 빌드 번호 충돌 등)가 실제 배포를 돌려봐야 드러나는 경우가 많아서, 설계 단계에서 모든 걸 예측하는 것보다 빠르게 돌리고 고치는 쪽이 더 확실했기 때문이다.

# 3. 모듈 구조: core/feature 경계가 흐려진 이유

## 3.1 상황

기능이 늘어나면서 라우팅이나 공유 로직 같은 게 core 패키지에 뒤섞이기 시작했다. 원래 core는 여러 feature가 공통으로 쓰는 것만 있어야 하는데, 특정 feature에서만 쓰는 로직까지 core에 들어가 있으니 feature 간 경계가 흐려지고 있었다.

## 3.2 판단

곧 카카오 로그인 같은 새 feature를 추가해야 하는 시점이었는데, 경계가 흐려진 상태로 새 feature를 더 얹으면 문제가 누적될 게 뻔했다. 그래서 새 기능을 얹기 전에 먼저 core/feature 경계를 정리하고, 의존성 주입 방식(getIt → injectable)도 함께 통일하기로 했다. "기능 추가 전에 구조부터 정리한다"는 순서를 택한 셈이다.

# 4. 카카오 OIDC: 로그인이 왜 이제야 필요했나

## 4.1 상황

앱에 로그인/회원가입 기능이 없어서, 구독이나 알림 설정 같은 사용자별 개인화 기능을 제공할 방법이 없었다. 초기에는 게스트 상태로도 핵심 기능(법안 조회 등)을 쓸 수 있게 설계했었기 때문에 로그인 없이도 서비스가 굴러갔지만, 개인화 기능을 붙이려면 사용자 식별이 필요한 시점이 왔다.

## 4.2 판단

소셜 로그인 중 카카오를 택한 이유는 국내 서비스 특성상 사용자 진입 장벽이 가장 낮은 옵션이었기 때문이다. OIDC 표준을 따르는 카카오 SDK를 사용해 도메인-뷰모델-프레젠테이션 레이어로 나눠 구현했고, 앞서 정리해둔 core/feature 경계 덕분에 로그인 관련 코드를 `features/lib/signup/`, `core/lib/oidc/`에 깔끔하게 위치시킬 수 있었다.

# 5. 결과

- 저장소 상태가 Slack으로 자동 공유되어 GitHub을 직접 열어보지 않아도 진행 상황 파악이 가능해짐
- 빌드→배포가 자동으로 이어지는 CI/CD 파이프라인이 구축되어, 이후 버전 20~24까지의 배포가 파이프라인을 통해 안정적으로 이뤄짐
- core/feature 경계 정리와 DI 통일로, 이후 카카오 로그인 같은 신규 기능을 일관된 구조로 추가할 수 있게 됨
- 카카오 소셜 로그인 기반 회원가입/로그인 플로우를 엔드투엔드로 구현, 개인화 기능의 기반을 마련
