# 들어가며

[인증 코어 모듈]({% post_url 2024-09-16-barlow-auth %})을 만들 때는 `Credential`/`Authenticator`/`Principal`이라는 추상화만 잡아뒀을 뿐, 실제로 검증하는 자격 증명은 회원번호 기반 하나뿐이었다. 카카오 소셜 로그인을 붙이면서 이 추상화가 두 번째 `Credential` 구현체를 처음 받아들이게 됐다.

이 글은 왜 회원가입 도메인 모델을 두 번이나 갈아엎었는지, 그리고 그 과정에서 확정한 설계를 정리한 것이다. 실제 코드 구조는 [구현 문서]({% post_url 2026-02-01-barlow-kakao-oidc-backend-implementation %})에서 다룬다. 모바일 쪽 카카오 SDK 연동은 [앱 자동화 파이프라인과 카카오 로그인]({% post_url 2026-02-27-barlow-front-cicd-auth %}) 글에서 별도로 다뤘다.

# 1. 상황: 왜 이제 와서 로그인이 필요했나

앱은 초기부터 게스트 상태로도 법안 조회 같은 핵심 기능을 쓸 수 있게 설계돼 있었다. 로그인 없이도 서비스가 굴러갔던 이유다. 하지만 구독·알림 설정처럼 사용자별로 다른 상태를 저장해야 하는 기능을 붙이려는 시점이 되자, 사용자를 식별할 방법이 필요해졌다.

# 2. 과제: 로그인=회원가입인 흐름을 어떻게 모델링할 것인가

소셜 로그인은 "로그인해보니 처음 온 사용자면 그 자리에서 회원가입까지 처리한다"는 흐름이 자연스럽다. 문제는 이걸 도메인으로 어떻게 표현하느냐였다.

- 카카오 `id_token` 검증은 기존 `Authenticator` 인터페이스로 표현 가능했지만, 그 뒤에 이어지는 "신규면 생성, 기존이면 로그인"이라는 분기는 인증(authentication)이 아니라 별개의 도메인 로직이었다.
- 약관 동의(Term/TermAgreement), 외부 인증 제공자 연결(AuthProvider), 탈퇴까지 포함하면 단순 로그인 기능이 아니라 계정 생명주기 전체를 다루는 문제가 됐다.

# 3. 판단: 두 번의 재설계

## 3.1 첫 시도 — RegistrationFlow

처음에는 회원가입 절차 자체를 `RegistrationFlow`라는 상태 객체로 모델링했다. 가입 절차를 하나의 흐름(flow)으로 보고, 그 흐름이 진행 상태를 들고 있는 방식이었다.

그런데 실제로 구현하다 보니 "흐름"이라는 개념이 무거웠다. 약관 동의, 사용자 생성, 인증수단 연결이 각각 독립적으로 실패/재시도될 수 있는 작업인데, 하나의 Flow 객체가 이 전부를 상태로 들고 있으려니 책임이 비대해졌다.

## 3.2 두 번째 시도 — Orchestrator, 그리고 다시 Service

`RegistrationFlow`를 걷어내고 `MemberRegisterOrchestrator`가 `MemberCreator`/`AuthProviderService` 같은 협력 객체를 조합하는 구조로 바꿨다. "흐름을 객체가 들고 있는" 방식에서 "오케스트레이터가 각 단계를 호출하는" 방식으로 전환한 것이다.

여기서 한 번 더 갈아엎었다. Orchestrator라는 이름이 암시하는 것과 달리, 실제로는 회원 생성 커맨드(`MemberCreateCommand`)와 승급 커맨드(`MemberPromoteCommand`)를 순서대로 실행하는 정도의 책임이었다. 그래서 최종적으로는 `MemberRegisterService`가 커맨드 객체들을 직접 실행하는, 더 단순한 구조로 정리했다.

## 3.3 왜 이 순서로 정리했는가

"Flow(상태 객체) → Orchestrator(조합 객체) → Service(커맨드 실행)"로 옮겨간 건, 매번 "이 책임이 정말 여기 있어야 하나"를 스스로 되물은 결과였다. 처음부터 정답을 알고 설계한 게 아니라, 구현하면서 책임이 안 맞는 지점을 계속 걷어낸 끝에 가장 단순한 형태로 수렴했다.

# 4. 함께 정리한 것들

- **약관 동의**: `Term`/`TermAgreement`를 회원가입과 별도 도메인으로 분리해, 약관 종류가 늘어나도 회원가입 로직을 건드리지 않게 했다.
- **탈퇴**: 회원가입의 반대 방향 흐름으로 `MemberUserWithdrawalProcessor`를 별도 구현했다 — 가입과 탈퇴를 대칭적인 하나의 로직으로 억지로 묶지 않았다.
- **패키지 구조**: account 도메인을 `create`/`device`/`login`/`term`/`withdrawal`/`authprovider`로 나누는 feature-first 구조로 재정리해서, 이후 인증수단이 늘어나도(예: 다른 소셜 로그인) 패키지 단위로 확장할 수 있게 만들었다.

# 5. 결과

카카오 OIDC 기반 회원가입~로그인 전체 흐름을 엔드투엔드로 구현했다. 이후 마무리 작업(2026-02-23~03-03)에서 내 계정 조회 API와 약관 동의 요구사항 조정으로 이어졌다.
