# 들어가며

[설명 문서]({% post_url 2025-04-12-barlow-front-notification-share %})에서 다룬 알림/공유 기능과 API 연동을, 실제로 어떤 순서로 구현했는지 정리한다.

# 1. FCM 알림 연동

## 1.1 기본 연동과 알림 센터

FCM(Firebase Cloud Messaging)을 연동하고, 수신한 알림을 모아 볼 수 있는 알림 센터 뷰를 추가했다. 이 시점에 후원(donation) 뷰도 함께 추가됐는데, 알림 센터에서 자연스럽게 이어지는 도입부 성격의 화면이었다.

이후 별도 개선 작업에서 알림 목록을 최신순으로 정렬하도록 바꾸고, 알림이 없을 때 보여줄 빈 상태(empty state) 문구를 추가했다 — 이런 디테일은 이 시기 이후 UX 다듬기 과정에서 이어졌다.

## 1.2 line separator 고정

FCM 연동 과정에서 사소하지만 실제로 문제가 됐던 것 하나: 줄바꿈 문자(line separator)를 LF로 고정하는 수정이 있었다. 여러 플랫폼(Android/iOS)에서 알림 payload의 텍스트를 렌더링할 때 줄바꿈 문자가 일관되지 않으면 레이아웃이 깨지는 경우가 있어, 이 시점에 명시적으로 고정했다.

# 2. 이미지 공유 기능

법안 정보를 이미지로 캡처해 공유하는 기능을 추가했다. 동시에 기존 태그 필터 로직을 리팩터링하고, 법안 발의자 목록 조회 기능과 사용자 정보를 저장하는 저장소를 함께 추가했다 — 공유 기능이 법안 상세 정보(발의자 등)에 의존했기 때문에 자연스럽게 같이 진행된 작업들이다.

# 3. 도메인별 API 정의와 라우터 추가

`core`에 요청/응답 형식을 정의하고 `feature/data`가 이를 참조하는 기존 구조([바로앱 아키텍처](https://ogongchill.github.io/posts/%EB%B0%94%EB%A1%9C%EC%95%B1%EC%95%84%ED%82%A4%ED%85%8D%EC%B3%90/) 문서에서 다루는 DIP 패턴)를 따라, 다음 순서로 도메인별 API를 정의하고 라우터를 추가했다.

```
auth  →  home  →  legislation(account) → menu → preannounce(입법예고) → recent-bill(최근 접수 법안)
```

각 도메인마다:

1. 요청/응답 DTO를 `core`에 정의 (json_serializable/freezed 기반)
2. `feature/data`에서 리포지토리 구현체가 해당 API 클라이언트를 참조
3. 화면(View)을 정적 목데이터에서 실제 리포지토리 호출로 전환

이 패턴을 반복해서 home view, 최근 접수 법안 view, 상임위원회 view, 입법예고 view, 알림 설정 view, 회원가입/로그인 view까지 순차적으로 실제 API에 연결했다.

# 4. 마무리 디테일

이 시기 막바지에 앱 로고와 스플래시 화면, 최근 접수 법안/입법예고 아이콘을 추가하며 화면의 시각적 완성도를 같이 끌어올렸다 — 기능적으로는 API 연동과 관계없지만, "정적 데모 → 실제 서비스" 전환이라는 이번 작업의 성격상 시각적 완성도도 같은 마일스톤 안에서 처리하는 게 자연스러웠다.

# 5. 남은 디테일은 다음 스프린트로

이 시점에는 알림 목록 정렬이나 빈 상태 문구 같은 UX 디테일까지는 다루지 않았다. 큰 기능(FCM, 공유, 도메인별 API 연동)을 먼저 끝내고, 세부 다듬기는 별도 작업으로 분리해 처리했다 — API 연동처럼 앱 전체의 동작 여부에 영향을 주는 작업과, 정렬/문구 같은 지엽적인 개선을 같은 커밋 묶음에서 다루지 않으려는 판단이었다.
